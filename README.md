# Supermarket app

Monorepo. The Django + DRF + PostgreSQL backend lives in `backend/`.

## Backend quickstart

```bash
docker compose up -d db mailpit
cd backend
python3.13 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
export DATABASE_URL=postgres://app:app@localhost:5434/app
python manage.py migrate
pytest
```

Nothing loads a `.env` file: `.env.example` only documents the variables. Export what you need
(the defaults already match the compose database on port 5434) or use `docker compose`, which
sets them for the `web` service. The dev compose file publishes the database and Mailpit ports on
`127.0.0.1` only.

Or run everything in containers: `docker compose up -d db && docker compose run --rm web pytest`.

Health check: `GET /healthz` returns `{"status": "ok"}`. Mailpit UI: http://localhost:8025.

## API contract

The OpenAPI 3 contract is committed at `backend/openapi.yaml` and served live (public, no auth) at
`GET /api/schema/` (YAML; add `?format=json` for JSON). It is the source for the Flutter client.

Regenerate it after changing any endpoint, serializer or `@extend_schema`:

```bash
cd backend
python manage.py spectacular --file openapi.yaml --validate --fail-on-warn
```

Drift is caught twice: `tests/test_openapi.py::test_committed_openapi_matches_generated` and a CI
step that regenerates the file and runs `git diff --exit-code`. Both fail if you forget to commit
the regenerated file. Every operation documents the standard error shape (`Error`: `code`,
`detail`, `fields`) as its `default` response. The same shape is returned for errors raised
outside the API views: unknown URLs (404), unhandled exceptions (500, never leaking exception
text), 400/403 and CSRF failures (`csrf_failed`) all answer JSON. Only `/admin/` keeps Django's
HTML error pages.

Client notes:

- Cursor pagination over mutable sort keys (shopping lists are ordered by `-updated_at`) can skip
  or repeat rows when data changes between page requests. Sync clients should use `updated_since`.
- Send `updated_since` in UTC with a `Z` suffix (`2026-11-02T10:00:00Z`). A literal `+00:00` must
  be URL-encoded (`%2B00:00`), otherwise `+` is read as a space.
- No CORS package is installed on purpose: the only client is a mobile app, which is not subject
  to browser CORS rules. Do not add `CORS_ALLOW_ALL`.

Generate a Dart client (not part of this repo), for example:

```bash
openapi-generator-cli generate -i backend/openapi.yaml -g dart-dio -o client
```

## Mobile app

The customer app (Android and iOS, French only) lives in `app/`. Flutter 3.24.2 (Dart 3.5.2) is
pinned in `app/pubspec.yaml` and in the CI job `app`.

Requirements:

- Flutter 3.24.2 (stable) on `PATH`.
- iOS: Xcode and CocoaPods. Deployment target iOS 14.0.
- Android: Android SDK (`ANDROID_HOME`), minSdk 24.
- Android builds need JDK 17. The Gradle wrapper is 8.3, which supports Java 17 up to 20; newer
  JDKs (21, 24, ...) fail (for example "Unsupported class file major version 65") until Gradle
  and the Android Gradle Plugin are upgraded together with Flutter. Point `JAVA_HOME` at a JDK 17,
  per command or in your shell profile. One way to get one is the runtime bundled with Android
  Studio (the `jbr` folder inside the Android Studio application bundle):
  `JAVA_HOME=/path/to/jdk17 flutter build apk --debug --dart-define-from-file=env/dev.json`.
- The SDK pins (`sdk: 3.5.2`, Flutter 3.24.2 in `app/pubspec.yaml`) are exact, so use exactly
  Flutter 3.24.2.

Run (backend on port 8000 of your machine):

```bash
cd app
flutter pub get
flutter run --dart-define-from-file=env/dev.json       # Android emulator
flutter run --dart-define-from-file=env/dev_ios.json   # iOS simulator
```

Environments (`app/env/*.json`, passed with `--dart-define-from-file`, read through `AppConfig`):

| File | `API_BASE_URL` | Use |
| --- | --- | --- |
| `env/dev.json` | `http://10.0.2.2:8000` | Android emulator (host loopback) |
| `env/dev_ios.json` | `http://localhost:8000` | iOS simulator |
| `env/staging.json` | `https://api.example.com` | placeholder |
| `env/prod.json` | `https://api.example.com` | placeholder |

Cleartext HTTP is allowed only for debug builds on Android (`android/app/src/debug`) and for
local networking on iOS (`NSAllowsLocalNetworking`).

Generated code convention: files produced by `build_runner` for the app (`*.g.dart`,
`*.freezed.dart`) are git-ignored and never committed; run
`dart run build_runner build --delete-conflicting-outputs` after `flutter pub get` (CI does too).
The only committed generated code is the API client under `app/packages/api_client/` (added later).
Localization (`app/lib/l10n/app_fr.arb`) is generated by `flutter pub get` or `flutter gen-l10n`.

Checks: `dart format --set-exit-if-changed . && flutter analyze && flutter test`.

## Language and currency

The API is French by default (`LANGUAGE_CODE = "fr"`; supported: `fr`, `en`). `LocaleMiddleware`
reads `Accept-Language`: no header, `fr`, `fr-CI`, `fr-FR` and unsupported languages (e.g. `de`)
answer in French; `Accept-Language: en` answers in English. Error `code` values (`validation_error`,
`not_found`, ...) are English snake_case in both languages, so clients should branch on `code` and
field keys, never on message text. The currency is `XOF` (override with `CURRENCY`); prices are whole
amounts. `TIME_ZONE` stays `UTC`.

- **OpenAPI stays English.** `backend/openapi.yaml` and `/api/schema/` are always rendered in
  English, whatever the language. `python manage.py spectacular` is a project command
  (`common/management/commands/spectacular.py`) that shadows the library one and generates under
  English; the CLI call above is unchanged. Keep `common` before `drf_spectacular` in
  `INSTALLED_APPS`.
- **Message catalog.** Django and DRF built-in messages (password validators, required, ...) are
  translated by Django. Our own custom validation messages (payments, accounts, shopping) live in
  the plain dict `common/messages.py` (`msg(key, **fmt)`, `msg_lazy` for import-time use), with a
  French and an English text per key (a test enforces both). No `.po`/`.mo` files.
- **Known gap.** These stay English: the JSON error `detail` written by `common/handlers.py` and the
  error handler, messages in `staff` and `uploads`, the Django admin and management commands. The
  mobile app does not display `detail`.

## Demo data

`python manage.py seed_demo` fills a development database (it refuses to run unless `DEBUG` is
true, which is the case with `config.settings.dev`). It is idempotent: re-running it keeps the same
rows and re-publishes the "Prospectus de la semaine" flyer for the current week if its dates have passed.

It creates Ivorian demo data: 6 French-named categories, 24 products, one published flyer with 12
offers in whole XOF amounts, 5 stores (Cocody, Marcory, Yopougon, Plateau, Bouaké) with opening
hours (Mon-Sat; Sunday closed except for Cocody), three payment methods (Wave
`+2250100000001`, Orange Money `+2250700000002`, MTN MoMo `+2250500000003`; obviously fake numbers,
created through `payments.services` so they are audited once and updated, never duplicated, on
re-runs), a staff user `staff@example.com` and a
customer `customer@example.com` (with loyalty card). No images are created.

Passwords come from `DEMO_STAFF_PASSWORD` and `DEMO_CUSTOMER_PASSWORD`. If unset, these dev-only
defaults apply (never use them anywhere real): staff `demo-staff-pass-123`, customer
`demo-customer-pass-123`.

## Staff users

Staff are never created through the API. A superuser (created with `createsuperuser`, below) gets
the role `staff` automatically and can promote other users to staff in the Django admin
(`/admin/`, Users, set the role). Locally, `seed_demo` already creates `staff@example.com`.

## Deployment

The hosting provider is still to be confirmed with the client. A single VPS running
`docker-compose.prod.yml` is sufficient for launch, and the same containers move unchanged to a
managed container platform later.

### What runs

| Service | Purpose |
| --- | --- |
| `migrate` | One-shot: `migrate --noinput` then `createcachetable`; `web` starts only after it succeeds. |
| `web` | The `backend/` image: gunicorn as non-root user `app`, `config.settings.prod`, health check on `/healthz`. |
| `caddy` | Automatic HTTPS (Let's Encrypt), reverse proxy to `web:8000`, request body capped at 6 MB. |
| `maintenance` | Runs `manage.py flushexpiredtokens` once a day (purges expired JWT blacklist rows). |
| `db` | Optional Postgres 16 with a named volume, only with `--profile with-db`. |

### Prerequisites

- A server with Docker and Docker Compose 2.20 or newer (`depends_on.required` is used), ports 80
  and 443 open.
- A DNS record for your domain pointing at the server (Caddy needs it to obtain the certificate).
- A Postgres database: a managed instance (recommended, give its URL in `DATABASE_URL`) or the
  bundled `with-db` profile.
- Optional: an S3-compatible bucket for images; Sentry DSN for error reporting.

### Environment variables

Set these in `.env.prod` (template with comments: `.env.prod.example`).

| Variable | Required | Default | Notes |
| --- | --- | --- | --- |
| `SECRET_KEY` | yes | none | At least 32 characters; the dev default is rejected. |
| `DATABASE_URL` | yes | none | Production never falls back to the dev database. |
| `ALLOWED_HOSTS` | yes | none | Comma-separated, no `*`. First entry is used by the health check. |
| `CSRF_TRUSTED_ORIGINS` | no | empty | Comma-separated origins with scheme. |
| `DOMAIN`, `ACME_EMAIL` | yes (Caddy) | none | Public host name and Let's Encrypt contact. |
| `CURRENCY` | no | `XOF` | Currency code shown to clients (CFA franc, no decimals in practice). |
| `SECURE_SSL_REDIRECT` | no | `1` | `/healthz` is always exempt. |
| `SECURE_HSTS_SECONDS` | no | `31536000` | `.env.prod.example` ships `3600`: keep it short for the first deploy until HTTPS is verified, then raise it to `31536000`. |
| `SECURE_HSTS_INCLUDE_SUBDOMAINS` | no | off | Set `1` only if all subdomains are HTTPS-only. |
| `AUTH_THROTTLE_RATE` | no | `10/min` | |
| `STAFF_SENSITIVE_THROTTLE_RATE` | no | `5/min` | Per-staff-user limit on creating/updating payment methods; every attempt counts, including wrong passwords. |
| `NUM_PROXIES` | no | `1` in prod, `0` otherwise | Number of reverse proxies in front of gunicorn (Caddy = 1); the auth throttle uses it to find the real client IP in `X-Forwarded-For`. Set `0` if gunicorn is exposed directly. |
| `ADMIN_ALLOWED_IPS` | yes (Caddy) | none | Space-separated IPs/CIDRs allowed to reach `/admin/`. Compose refuses to start without it. |
| `WEB_CONCURRENCY` | no | `3` | gunicorn workers. |
| `LOG_LEVEL` | no | `INFO` | Logs go to stdout/stderr. |
| `SENTRY_DSN` | no | empty | Sentry is initialized only if set. |
| `SENTRY_ENVIRONMENT`, `SENTRY_TRACES_SAMPLE_RATE` | no | `production`, `0.0` | |
| `AWS_STORAGE_BUCKET_NAME` | no | empty | Set to use S3 for uploads; otherwise the `media` volume. |
| `AWS_S3_ENDPOINT_URL`, `AWS_S3_REGION_NAME`, `AWS_S3_CUSTOM_DOMAIN` | no | empty | S3 options. |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` | with S3 | empty | |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | `with-db` only | `app` / none / `app` | |

### First deploy

All commands run from the repository root. `--env-file .env.prod` feeds the Caddy and Postgres
values; the app containers also read `.env.prod` directly.

Create `.env.prod` before running any `docker compose -f docker-compose.prod.yml ... config`
or `up`; compose fails on the missing `env_file` and on required `${...}` values otherwise.
Use a short `SECURE_HSTS_SECONDS` (for example `3600`) for the first deploy and raise it to
`31536000` once HTTPS works, because browsers remember HSTS.

```bash
cp .env.prod.example .env.prod          # then edit every value; generate SECRET_KEY as the file says
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
# with the bundled database: add `--profile with-db` (and set DATABASE_URL to the db service)
curl https://api.example.com/healthz     # {"status": "ok"}
```

Create the first staff user (a superuser; it gets the role `staff`):

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm web python manage.py createsuperuser
```

Then sign in at `https://<domain>/admin/` to promote further staff.

### Securing /admin

Caddy only forwards `/admin/*` to clients whose IP is in `ADMIN_ALLOWED_IPS` (space-separated
IPs or CIDRs, for example your office or VPN range); everyone else gets `403 Forbidden`. The
variable is mandatory so the choice is deliberate (`0.0.0.0/0 ::/0` allows everyone and is not
recommended). Also use strong, unique staff passwords and consider reaching the admin only through
a VPN. There is no two-factor authentication in v1. The API under `/api/v1/` is not affected.

### Media storage

- With S3 (`AWS_STORAGE_BUCKET_NAME` set), uploads go to `uploads/*` in the bucket. Because the
  storage uses `querystring_auth=False` and `default_acl=None`, the returned image URLs are plain
  URLs, so the bucket (or CDN in front of it) must allow public read of `uploads/*`. Minimal
  bucket policy (replace `BUCKET`):

  ```json
  {
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::BUCKET/uploads/*"
    }]
  }
  ```

  Also turn on bucket versioning so overwritten or deleted images can be recovered.
- Without S3, files live in the `media` volume. Enable the commented `/media/*` block in
  `deploy/Caddyfile` so Caddy serves them, and include the volume in backups.

### Notes on behavior

- The auth throttle counts requests in the database cache table (`django_cache_table`, created by
  `createcachetable` in the `migrate` service), so the limit holds across gunicorn workers.
- Caddy rejects request bodies over 6 MB before Django sees them; the application limit for an
  image file itself stays 5 MB.
- Expired refresh tokens are purged daily by the `maintenance` service. Alternative: remove that
  service and use host cron:
  `0 3 * * * cd /srv/app && docker compose -f docker-compose.prod.yml --env-file .env.prod run --rm web python manage.py flushexpiredtokens`.
- Admin static files are collected into the image at build time and served by WhiteNoise.

### Backups

- Managed Postgres: enable daily automated snapshots and point-in-time recovery.
- `with-db` profile: nightly dump from cron, copied off the server, for example:
  `0 2 * * * cd /srv/app && docker compose -f docker-compose.prod.yml --env-file .env.prod exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' | gzip > /backups/app-$(date +\%F).sql.gz`
- Media: S3 bucket versioning, or a copy of the `media` volume.

### Upgrades and rollback

Upgrade: `git pull`, then re-run `docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build`.
The `migrate` service applies new migrations before `web` restarts. Migrations are forward-only,
so take a database backup first. To roll back code, check out the previous revision and re-run
the same command; if a release included a migration that is not backward compatible, restore the
backup instead.
